# LEO Network Simulator

저궤도 위성망의 패킷 전달과 라우팅 알고리즘을 비교하는 Windows용 시뮬레이션 프로그램입니다. INI 시나리오 편집, 단독 시뮬레이션 실행, 지도 재생 및 실행 결과 비교를 제공합니다.

앱 상단 문서 아이콘에서 사용자 설명서를 열 수 있습니다. 설명서에서 **PDF 저장**을 누르면 브라우저의 인쇄 창에서 PDF로 저장할 수 있습니다. [웹 설명서](manual/index.html)

본 문서는 실행 엔진 4.x 및 `leo-native-replay-v4` 결과 형식을 기준으로 합니다.

## 1. 구성 및 지원 범위

| 구분 | 지원 내용 |
|---|---|
| 라우팅 | Dijkstra 지연 최소·홉 최소, MCSR-LS·TS·HR |
| 위성망 | Walker-Delta 위성군, 위성 간 링크(ISL), 지상 링크(GSL) |
| 트래픽 | 지상국·이동 노드의 패킷 송신, 전송률·패킷 크기·송신 구간 설정 |
| 전송 | 링크별 FIFO 큐, 직렬화·전파 지연, 큐 초과 및 연결 단절에 따른 폐기 |
| 시나리오 | 고정·무작위 장애, 링크 개폐 일정, 구역별 혼잡·지연·지터·손실 |
| 제어 통신 | 연결 감시, 상태 광고, DS 보고·투표·인계, CSIB 배포 |
| 결과 | 지도·경로 재생, 전달률·지연·지터·제어 전송량·연산 계측 |

원본 MCSR 순수 코어와 궤도 코드는 `engine/vendor/`에 보관합니다. 파일 해시는 `engine/vendor/routing-origin.json`과 `engine/vendor-origin.json`으로 확인합니다. 패킷 스케줄러, 제어 전송 모델, 설정 해석기와 UI는 본 프로그램의 실행 기반입니다.

## 2. 실행 환경

- Windows 10/11, x64
- Microsoft Edge WebView2 Runtime 및 Windows UI 호스트에 필요한 .NET Framework
- 활성 저장 폴더에 대한 쓰기 권한

배포 EXE에는 Python 실행 환경이 포함되어 있습니다. 실행 시 별도 Python 설치, 원본 프로젝트, OMNeT++, INET, WSL 또는 Docker가 필요하지 않습니다. WebView2 등 시스템 런타임 설치 파일은 배포본에 포함하지 않습니다.

웹 UI와 실행 관리기는 Windows가 할당한 포트에서 `127.0.0.1`로만 접속합니다. 외부 서버, 계정 또는 데이터베이스를 사용하지 않습니다.

### 사용자 설정과 결과

배포 EXE는 프로그램 폴더의 `settings`를 사용합니다. 실행 결과는 기본적으로 같은 폴더의 `data/runs`와 `data/experiments`에 저장합니다. 다른 위치는 **설정 파일·저장 위치 → 실행 결과 저장 폴더 → 폴더 선택**에서 지정합니다. 앱을 다시 열면 선택한 폴더 바로 아래의 `runs`와 `experiments`를 사용합니다. 기존 결과는 원래 위치에서 **실행 결과 열기 → 외부 폴더 열기**로 재생할 수 있습니다. 결과 위치를 바꿔도 설정은 프로그램 폴더에 유지됩니다.

시작 및 오류 로그는 프로그램 폴더의 `logs/app.log`에 최근 4개 파일까지 남습니다. 개별 엔진 출력은 실행 폴더의 `run.log`에 있습니다. 앱 종료 시 실행 중인 엔진을 정리하며, 새 결과는 `completed.json`이 생성된 뒤 목록에 나타납니다. 바탕화면에서 실행하려면 프로그램 폴더의 EXE 바로가기를 사용합니다.

## 3. 시작하기

1. 배포 ZIP 전체를 한 폴더에 압축 해제합니다.
2. `sim-ui.exe`를 실행합니다. EXE만 다른 위치로 옮기지 않습니다.
3. **시험 조건**과 **알고리즘**을 선택합니다. 세부 값은 **조건 수정**에서 변경합니다.
4. **INI에 저장**한 뒤 선택한 시나리오를 실행합니다.
5. 실행이 완료되면 지도와 통계를 확인합니다.

**비교 실행**에서는 여러 알고리즘을 선택할 수 있습니다. 공통 입력을 확정한 후 알고리즘을 순차 실행합니다. 중단한 실행은 완료 결과로 등록하지 않으며, 직전 완료 결과를 유지합니다.

| 실행 방법 | 기능 |
|---|---|
| `sim-ui.exe` | 설정 편집, 새 계산, 비교 실행, 결과 재생 |
| `start_ui.bat` | 소스 실행. Python 및 `requirements-build.txt` 의존성 설치 필요 |
| `index.html` 직접 열기 | 보관된 결과 재생. 새 계산과 로컬 INI 편집은 EXE에서 수행 |

## 4. 시나리오 설정

공통 진입 설정 파일은 다음과 같습니다.

```text
settings/simulations/Network/scenarios.ini
```

`Network` 폴더에는 알고리즘 공통 설정과 지상 노드·외부 시나리오 자료가 있습니다. `Dijkstra132`, `Mcsr132`, `PaperS1Mcsr` 등은 개별 실행 구성의 이름입니다.

UI 편집과 **INI 파일** 버튼을 통한 텍스트 편집을 지원합니다. INI의 `include`, `extends`, 기존 설정 키를 유지하며, 저장한 결과 내부의 INI 사본은 현재 설정을 수정해도 변경되지 않습니다.

메인 화면의 **시험 조건**은 통신·부하·장애 등 시험 환경을 선택합니다. 자주 쓰는 조건을 먼저 표시하며, **추가 시험 표시**를 켜면 INI에서 <code>additional = true</code>로 지정한 시험도 선택할 수 있습니다. **알고리즘**은 별도 항목에서 선택하며 변경 즉시 현재 INI 구성에 저장합니다. 저장된 결과의 알고리즘과 지도는 바뀌지 않으며 **실행**하면 새 결과를 생성합니다. 표시 이름은 INI의 <code>displayName</code>에서 바꿀 수 있습니다. 값을 생략하면 INI 섹션 이름을 표시합니다. 원문은 **설정 파일·저장 위치 → INI 파일 열기**에서 확인합니다.

**조건 수정 → 기본값**을 누르면 선택한 구성에 제공된 INI 설정을 편집 화면에 불러옵니다. **INI에 저장**을 눌러야 적용되며, 취소하면 현재 설정으로 돌아갑니다. 상속값은 현재 상위 구성의 값을 따릅니다. 직접 추가해 제공 기본값이 없는 구성은 기본값을 불러올 수 없습니다. 목록 아래의 설명은 현재 설정에 맞춰 바뀌며, ⓘ 아이콘으로 개별 값과 화면의 사용법을 확인할 수 있습니다.

설정 화면은 기본 설정·트래픽·링크·장애·환경 조건을 중심으로 구성합니다. MCSR 옵션은 해당 알고리즘을 선택했을 때 표시하며, TS 지연 한도와 HR 지터 한도는 각 알고리즘에서만 표시합니다. **고급 설정**에는 경로 계산, 제어 통신, 공통 SRD, 모델 검증과 기록 옵션을 모았습니다. 처리 지연 가정·시간 기반 제어·비용 기반 지터가 활성화되면 화면 위에 적용 상태를 표시합니다. 숨겨진 옵션과 수정하지 않은 INI 값은 저장 시 유지합니다.

### 실행 구성 추가

기존 구성의 상속으로 새 구성을 정의할 수 있습니다. [사용자 설명서의 INI로 시험 추가](manual/index.html#add-trial)에서 편집, 새로고침, 시험 선택 순서와 주요 INI 항목을 확인할 수 있습니다.

```ini
[Config ExperimentA]
displayName = "내 경로 비교 시험"
extends = Mcsr132
sim-time-limit = 60s
seed-0-mt = 23542
*.satellite[*].net.routingType = "Sat_Net_McsrRouting"
*.satellite[*].net.routing.algorithm = "mcsr-hr"
*.satellite[*].net.routing.service = "HR"
```

지원하는 단위와 수식은 프로그램의 설정 해석 범위에 한정됩니다. OMNeT++의 모든 실행 표현식과 NED 모델을 해석하지 않습니다. 원본 INI에 남아 있는 PHY·통계 기록 설정이 모두 계산에 반영되는 것은 아니며, 지원 항목은 설정 화면과 `native_engine.py`의 설정 계약을 기준으로 합니다.

예를 들어 특정 노드의 송신 간격은 다음과 같이 설정할 수 있습니다.

```ini
*.station[0].traffic.sendInterval = 0.00001s
```

이는 해당 노드에서 초당 100,000개 패킷을 발생시키는 설정입니다. 지원 시간 해상도는 10⁻¹¹초이며, 실제 실행 시간과 결과 크기는 송신 노드 수·패킷 크기·위성 수·제어 트래픽에 따라 증가합니다.

### 주요 실행 모델

| INI 키 | 기본값 | 의미 |
|---|---|---|
| `*.native.processingMode` | `"neutral"` | 알고리즘별 추가 가정 지연을 적용하지 않음. `"assumed"`는 설정한 처리 지연 적용 |
| `*.native.controlMode` | `"packet"` | `"packet"`은 제어 메시지를 실제 큐·링크에서 처리하며 DS·CSIB를 지원합니다. `"time"`을 설정에서 저장하면 CSIB를 끕니다. |
| `*.native.jitterModel` | `"packet"` | 패킷 도착 시간에 지터 반영. `"cost"`는 경로 비용에만 반영 |
| `*.native.islMode` | `"fixed"` | 고정 ISL 격자. `"scheduled"`는 해당 격자 안의 개폐 일정 적용 |
| `*.native.controlRefresh` | `5` | 제어 상태 관측·갱신 주기(초) |
| `*.native.controlTimeout` | `3` | 지역 보고 수집 제한 시간(초) |
| `*.native.controlResyncInterval` | `30` | 변경 광고와 별도의 재동기화 주기(초) |
| `*.native.controlMtu` | `1500` | 제어 프레임 최대 전송 크기(B). 허용 범위 64–65,535 |
| `*.native.controlReassemblyTimeout` | `3` | 첫 프레임 도착 후 재조립 제한 시간(초) |

실제 송신으로 큐 부하를 만드는 `actual` 모드와, 지정한 혼잡도·지연·손실 등을 주입하는 `environment` 모드는 구분해 기록합니다. 위성군·링크·송신·장애·SRD·MCSR 옵션은 시나리오 설정의 각 항목에서 변경할 수 있습니다.

### ISL 개폐 일정

기존 시나리오에 저장된 일정과 INI에서 지정한 CSV를 사용할 수 있습니다. INI에서 개폐 일정을 지정할 때는 `*.native.islMode = "scheduled"`를 설정하고 `*.native.islScheduleFile`에 CSV 경로를 적습니다. 조건 수정 화면에는 저장된 개폐 일정이나 장애 기록이 적용될 때만 상태가 표시됩니다. CSV 상대 경로는 진입 INI 파일이 있는 폴더를 기준으로 해석합니다.

```csv
time,event,satA,satB
10,failure,0,1
20,restore,0,1
```

시간 단위는 초입니다. `failure`/`restore` 외에 기존 `fail`, `down`/`up`도 읽습니다. 고정 Walker 격자 밖의 연결을 추가하거나 이웃 위성을 교체하는 일정은 지원하지 않습니다.

## 5. 알고리즘 비교 조건

비교 실행은 다음 순서로 처리합니다.

1. INI와 외부 입력을 읽어 공통 설정을 확정합니다.
2. 유효 K/L, 위성별 SRD 매핑과 SRD 대상 링크를 결정합니다.
3. 고정·무작위·구역 장애와 개폐 일정을 공통 물리 사건으로 확정합니다.
4. 같은 공통 입력과 송신 조건으로 알고리즘을 순차 실행합니다.

`route@T` 장애 대상은 지정된 고정 출발·목적 흐름의 전파 지연 최소 기준 경로에서 선정합니다. 비교 알고리즘이 선택한 경로에 따라 장애 대상을 바꾸지 않습니다. 기준 흐름이 모호하거나 기준 경로에 ISL이 없으면 준비 단계에서 오류를 반환합니다.

비교 판정에는 공통 설정, 물리 사건, SRD, 송신 입력과 엔진 식별값을 사용합니다. 알고리즘별 설정 차이는 별도로 표시합니다. 이전 결과 형식, 다른 엔진 또는 다른 모델 조건을 동일 조건의 v4 비교로 표시하지 않습니다.

## 6. 제어 통신 모델

초기 네트워크 정보는 공통으로 설치된 상태에서 시작하며, 이후 변경의 감지·전달·적용을 측정합니다. 기본 SLS 감시 간격은 0.2초, 장애 판단 기준은 3회 누락입니다.

- Dijkstra 및 CSIB 비활성 MCSR: 상태 광고 플러딩
- CSIB 활성 MCSR: DS 대상 보고·투표·인계의 유니캐스트, 지역 요청·CSIB의 브로드캐스트, DS 간 요약 유니캐스트
- 중간 전달 노드: DS 대상 보고를 자신의 라우팅 정보에 적용하지 않음
- 상태 변경 광고: 광고한 변경분을 해제하고 재동기화와 독립적으로 처리

제어 프레임과 데이터 패킷은 같은 FIFO 큐와 링크 용량을 사용합니다. 큐 용량은 대기 단위의 개수 기준이며 현재 전송 중인 단위는 대기 큐에 포함하지 않습니다. 제어 메시지는 전송 헤더 24B와 분할 헤더 16B를 포함한 MTU 이하의 프레임으로 나뉩니다. 기본 메시지 헤더는 32B, 링크 상태 레코드는 48B입니다.

각 홉에서 메시지를 완전히 재조립한 뒤 정보 적용 또는 다음 홉 전달을 수행합니다. 부분 손실이나 재조립 만료 시 해당 메시지를 적용하지 않습니다. 자동 프레임 재전송은 없으며, 이후 광고·지역 수집·재동기화로 정보를 회복합니다. 데이터 패킷 분할은 이 모델에 포함하지 않습니다.

## 7. 결과 저장 및 재생

```text
data/
├─ experiments/<실험 ID>/   공통 입력·SRD·물리 사건·실행 목록
├─ runs/<실행 ID>/          알고리즘별 완료 결과 및 진단 파일
├─ latest.json              최근 완료 결과 ID
└─ latest_result.js         HTML 직접 열기용 최근 완료 결과
```

| 파일 | 내용 |
|---|---|
| `manifest.json` | 결과 형식, 실행 ID, 진입 INI, 모델·엔진 정보, 파일 해시 |
| `config/` | 실행 당시 실제 사용한 INI 및 include 파일 사본 |
| `normalized.json` | 엔진에 전달한 정규화 설정과 확정된 공통 입력 |
| `engine-input.json` | 해당 실행의 엔진 입력 |
| `common-srd.json` | 유효 K/L, 위성별 SRD, SRD 대상 링크 |
| `physical-events.json` | 확정된 물리 연결 전이 |
| `routes.csv` | 라우팅 시점의 계획 경로와 계산 비용 |
| `summary.json` | 데이터 전달·흐름별 통계, 제어 전송 및 연산 계측 |
| `timeseries.csv` | 흐름별 시간 구간 통계 |
| `control-series.csv` | 시간별 누적 제어 계측 |
| `network-events.jsonl` | 장애·혼잡·SRD·CSIB 등의 사건 |
| `failures.csv` | 장애·복구 전이의 CSV 기록 |
| `inputs/` | 사용한 외부 시나리오·장애 입력 사본 |
| `events.csv` | 선택적으로 보관하는 상세 데이터 패킷 기록 |
| `run.log` | 엔진 실행 진단 |

개별 제어 프레임과 재조립 사건은 `packetTrace`를 켠 경우에만 `network-events.jsonl`에 기록합니다. `manifest.files`에 등록된 파일은 결과를 읽을 때 해시로 검사합니다.

### 실행 결과 열기

**실행 결과 열기**에서는 `manifest.json`이 있는 폴더를 선택합니다. 지도 좌표는 보관된 설정과 SGP4 모델로 재현하며, 장애·혼잡·CSIB 상태는 저장된 사건을 반영합니다. 매 시각의 좌표 전체를 저장한 동영상 형식은 아닙니다.

`routes.csv`는 원래의 11개 열을 유지합니다.

```csv
time,route,source,station,firstSat,exitSat,satHops,uplinkMs,satToStationMs,totalMs,path
```

이 파일의 지연은 라우팅 시점의 계산값이며 수신 패킷의 종단 간 지연과 다릅니다. 경로 행 수 역시 전달 성공 패킷 수가 아닙니다. `changes` 기록 모드에서는 경로가 바뀔 때만 행을 추가합니다.

대용량 CSV는 파일을 나눠 읽고 모든 경로를 압축 수치 배열에 보관합니다. 경로를 샘플링하거나 삭제하지 않으며, 재생 화면의 누적 통계는 전체 행을 기준으로 계산합니다. 초기 화면은 설정 미리보기를 먼저 표시하고 결과를 확인한 뒤 기록된 실행 화면으로 전환합니다.

결과 폴더를 열 때는 `manifest.json`에 등록된 파일만 읽습니다. 중복된 `result.json`이나 선택적 상세 첨부 파일을 함께 메모리에 적재하지 않습니다. `data/runs` 상위 폴더 전체가 아닌 개별 실행 ID 폴더를 선택합니다. 브라우저가 폴더 파일을 읽지 못하면 프로그램에 보관된 동일 ID의 결과를 불러오고, 보관본을 사용했음을 화면에 표시합니다. 파일 내용이나 해시가 잘못된 경우에는 이 복구 경로를 사용하지 않습니다.

EXE에서는 파일별 결과를 읽으며, 새로 생성되는 대용량 CSV를 중복 JSON·JavaScript 문자열에 포함하지 않습니다. HTML 직접 열기에서 대용량 결과의 전체 재생이 필요하면 실행 결과 폴더를 선택합니다.

기존 v1·v2·v3 결과는 보관된 경로와 해시를 유지한 채 읽습니다. 현재 설정 폴더를 `Network`로 이전해도 이전 결과 내부 파일은 변경하지 않습니다.

## 8. 지표 정의

| 지표 | 정의 |
|---|---|
| 발생 패킷 | 접속·초기 경로 선택 실패를 포함한 전체 송신 시도 |
| 전달률 | 수신 패킷 ÷ 발생 패킷 × 100 |
| 실패 패킷 | 송신 전 실패 및 큐·경로·링크·홉 제한 등에 따른 폐기 |
| 전송 중 | 종료 시점에 아직 수신·실패로 확정되지 않은 데이터 패킷 |
| 수신 지연 | 수신된 패킷의 생성부터 수신까지 걸린 시뮬레이션 시간 |
| 지연 표준편차 | 흐름별 수신 지연 표본의 표준편차 |
| 수신 지터 | 연속 수신 패킷의 지연 차이를 이용한 지수 평활 추정값 |
| 처리량 | 수신한 데이터 페이로드 비트 수 ÷ 전체 실행 시간 |
| 제어 전송량 | 프레임 헤더와 중단·종료 시 부분 전송을 포함한 사용 바이트 |
| 정보 수렴 | 대상 링크 양끝의 사건 이후 상태 정보를 모든 노드가 적용하기까지 걸린 시간 |
| 첫 수신 복구 | 영향을 받은 흐름에서 사건 후 생성된 첫 패킷을 수신하기까지 걸린 시간 |
| 안정 복구 | 연속 두 관측 구간에서 최소 패킷 수와 전달률 기준을 충족한 시각 |
| 계산 시간·연산량 | 호스트에서 측정한 계산 시간과 알고리즘 연산 카운터 |

데이터 패킷은 `발생 = 수신 + 실패 + 전송 중` 관계로 검증합니다. 논리 제어 메시지와 프레임 계측은 구분하며, 종류별 상세 값은 `summary.json`의 `control.byKind`에 저장합니다.

수신 패킷이 없으면 수신 지연을 유효한 0으로 해석하지 않습니다. 복구·수렴은 같은 링크의 다음 전이 또는 실행 종료까지 집계합니다. 관측이 끝날 때까지 기준을 충족하지 못하면 확인되지 않은 값으로 기록합니다.

호스트 계산 시간은 PC 성능과 동시 작업의 영향을 받습니다. `neutral` 모드에서 이 시간을 패킷 지연에 자동 합산하지 않습니다. `jitter_ms` 주입값은 추가 링크 지연의 표준편차이며, `packet` 모드는 0부터 2√3σ까지의 균등 추가 지연과 그 평균을 반영합니다. 라우팅용 지터 비용과 수신 지터 통계는 별도 지표입니다.

## 9. 모델의 경계

- 제어 통신은 본 프로그램의 독립 실험 규격입니다. 원 논문의 통신 규격·결과 수치 또는 실제 위성 장비 성능과의 동등성을 보증하지 않습니다.
- ISL은 고정 Walker 격자 안에서 개폐합니다. 다른 이웃으로 연결 대상을 교체하는 핸드오버는 지원하지 않습니다.
- LoRa 무선 물리계층, 충돌·에너지·IoT 단말 모델, TLE 입력 및 Walker-Star는 지원 범위에 포함하지 않습니다.
- 원본 프로젝트와 이벤트 순서·난수 소비·전체 패킷 결과가 동일하다는 의미의 호환 시뮬레이터는 아닙니다.
- 동일 조건 비교 판정은 입력의 일치를 확인하는 기능입니다. 특정 연구 가설이나 알고리즘 우열을 자체적으로 인증하지 않습니다.
- 위성 수, 송신률, 광고·재동기화 빈도가 높아질수록 실행 비용이 증가합니다. 실행 관리기는 엔진 메모리 4GiB 초과를 감지하면 실행을 중단합니다.

## 10. 개발 및 검증

개발·패키징 기준은 Windows Python 3.12입니다. C++ 빌드에는 WSL Ubuntu와 `g++-mingw-w64-x86-64`가 필요합니다. 브라우저 시험에는 Node.js와 기본 설치 경로의 Google Chrome이 필요합니다.

프로젝트 루트에서 실행합니다.

```powershell
python -m pip install -r requirements-build.txt
python engine/build.py
python -m unittest discover -s . -p "test_*.py" -v
node test_csv.js
node test_replay.js
node test_browser.js
python verify_workloads.py
python verify_workloads.py --control
```

네이티브 빌드는 Dijkstra·제어 전송 검사와 원본 MCSR 코어 검증을 수행합니다. 부하 검증은 1,584개 위성·100개 지상국에서 5개 알고리즘의 10–60Mbps 짧은 실행 55회, 10/35/60Mbps의 600초 실행 15회로 구성됩니다. 데이터 부하 행렬은 `controlMode=time`, `csibEnabled=false`, `processingMode=neutral`로 제어 트래픽을 제외하고 데이터 패킷 처리와 큐를 검증합니다. 이 결과를 실제 제어 오버헤드의 비교 결과로 사용하지 않습니다.

데이터 부하 검증은 활성 송신 노드의 송신 종료 시각도 시험 종료 시각에 맞춥니다. 준비·종료 관측 구간은 0으로 고정하고, 설정한 시작 시각·송신 간격·종료 시각으로 예상 발생 패킷 수를 별도로 계산해 실제 발생 수와 대조합니다. 원래 시나리오의 200초 송신 종료가 남아 있는 기록은 600초 지속 부하의 근거로 사용하지 않습니다. 이 시험은 시드 0의 실행 안정성·용량 점검이며 다중 시드의 통계적 성능 우열 검증과 구분합니다. 실행 시간은 병렬 작업과 PC 상태의 영향을 받고 메모리는 주기적으로 관측한 값입니다.

`--control`은 같은 위성·지상국 규모에서 알고리즘 5종을 각각 20초 실행합니다. `controlMode=packet`, CSIB 활성, 수집·투표 주기 5초, 재동기화 주기 10초로 실제 제어 전송과 큰 메시지 분할을 검사합니다. 두 시험 모두 패킷 수 보존, 공통 입력·SRD 일치 및 메모리 한도를 확인합니다. 프로그램의 기본 제어 설정은 이 검증용 프로파일과 별개입니다.

궤도 재생의 검증 자료는 [REPLAY_NOTES.md](REPLAY_NOTES.md), 알고리즘 확장 인터페이스는 [engine/README.md](engine/README.md)를 참조합니다.

### 연구 검증과 반복 비교

**비교 실행**에서 1회, 예비 시험 10회 또는 최종 비교 30회를 선택합니다. 고급 설정에서 시작 시드·준비 구간·종료 관측 구간을 지정할 수 있습니다. 반복 횟수는 시드 수이며, 총 실행 수는 시드 수 × 알고리즘 수입니다.

비교 실행의 기본 방식인 **자동**은 Windows의 메모리 여유와 논리 프로세서 수에 따라 같은 시드의 엔진을 최대 2개 실행합니다. **순차**는 한 번에 한 엔진을 실행합니다. 각 실행의 performance.json에는 실행 방식, 공통 준비·개별 준비·엔진·결과 저장 시간, CPU 시간과 최대 메모리를 보관합니다. 자동 실행의 호스트 경과 시간에는 자원 경합이 반영될 수 있습니다.

개발 계측은 `engine.exe <입력 JSON> <결과 폴더> --profile`로 실행합니다. `profile.json`은 시뮬레이션 진행 중에도 갱신되며, 분류별 이벤트 수와 표본 시간, 지상 링크 갱신 시간, 라우팅 함수의 포함 시간을 기록합니다. 이벤트 처리 시간에는 내부 함수 호출이 포함됩니다. 라우팅 시간과 지상 링크 시간을 이벤트 시간에 다시 합산하면 중복 계측됩니다.

 기본값 1회에서는 기존 비교 방식으로 실행합니다. 30회는 최종 비교용 분류이며 검증 인증이나 통계적 충분성을 보장하는 기준이 아닙니다.

같은 시드의 알고리즘들은 동일한 송신 입력·물리 사건·SRD를 사용합니다. 시드마다 준비한 입력을 보관하고 알고리즘 실행 순서를 순환합니다. 통계는 첫 번째 선택 알고리즘을 기준으로 시드별 차이에 대해 계산합니다. 통계 단위는 시드별 짝입니다. 같은 송신·물리 사건 입력을 반복하고 링크 난수를 사용하지 않으면 고정 입력 반복으로 표시합니다. 입력 중복이 있거나 기존 기록에서 변동 여부를 평가할 수 없으면 평균 차이만 표시합니다. 링크 난수 사용 횟수는 어떤 시드에서 난수가 실제 소비됐는지 알려주며, 망 규모·부하·장애 강도를 바꾸는 민감도 시험은 별도입니다. 표준 라이브러리로 고정 통계 시드 23542, 10,000회 짝지은 백분위 부트스트랩의 95% 신뢰구간을 산출합니다. 성능 승자는 자동 판정하지 않습니다. 시드 변화로 표현되지 않는 모델 오차는 이 신뢰구간에 포함되지 않습니다.

수신 지연·지터를 측정할 수 없는 실행은 해당 지표의 누락 시드로 남기고, 관측한 실행만으로 신뢰구간을 만들지 않습니다. 첫 수신과 안정 복구의 미관측 비율은 영향을 받은 흐름·장애 쌍을 분모로 사용합니다. 같은 링크의 다음 전이 또는 실행 종료까지 기준을 만족하지 못한 항목을 집계합니다. 영향을 받은 흐름이 없으면 해당 비율은 비어 있습니다. 수신 지터는 흐름별 EWMA 추정값의 수신 수 가중 평균이며, 독립적인 링크 비용 지터와 구분합니다.

```ini
*.native.warmupSeconds = 0
*.native.drainSeconds = 0
```

두 값의 기본값은 0입니다. 값을 지정하면 전체 실행 시간 중 준비 구간 이후부터 종료 관측 구간 이전까지 생성된 패킷을 측정 대상으로 삼습니다. 종료 관측 구간에는 새 데이터 패킷 생성을 중단하고 기존 데이터와 제어 통신을 계속 처리합니다. 준비 구간의 패킷도 부하에는 기여하지만 측정 코호트에서는 제외합니다. 시간 구간은 시작 포함·끝 제외이며 종료 시점에 남은 패킷은 `inFlight`입니다.

새 코호트 통계는 `summary.json`의 `measurement`에 `schema=1`, `metricVersion=cohort-1`로 저장합니다. 기존 전체 실행 v4 통계와 결과 형식은 유지합니다. 코호트 처리량은 관측 종료까지 수신한 코호트 페이로드 비트를 측정 대상 생성 구간의 길이로 나눈 값입니다. 제어 전송량·연산량·복구는 전체 실행을 대상으로 하므로 코호트 통계와 분리해 표시합니다.

반복 실험은 `data/experiments/<ID>/`에 시드별 공통 입력, 진행·완료 상태와 `statistics.json`을 저장합니다. 중단·실패한 실험은 완료된 반복 실험 통계로 표시하지 않습니다. **실행 비교 → 반복 실험 → 통계 보기**에서 완료된 이력을 다시 열 수 있습니다. 새 로컬 API는 `GET /api/experiments`, `GET /api/experiments/<ID>`이며, 기존 `POST /api/experiments`는 선택적 `research` 객체(`repetitions`, `seedStart`, `warmupSeconds`, `drainSeconds`)를 받습니다.

```powershell
# 전체 원본 코어 시험, 독립 정답, 패킷 커널, 반복 흐름, Python·브라우저 시험
python verify_research.py
# 빌드된 시험 실행 파일을 재사용
python verify_research.py --skip-build
# 기본 CSIB 주기의 장기 제어 시험: 132위성, 600초, 알고리즘 5종
python verify_workloads.py --long-control
```

검증 로그와 보고서는 `data/validation/`에 보관합니다. 부하 시험 캐시는 입력·엔진·검증 코드 및 검사 대상 출력 파일 해시가 모두 일치할 때만 재사용합니다. 검증 보고서에는 엔진·소스·원본 파일 해시, 실행 환경, 시험별 로그 해시와 통과 범위를 남깁니다. `verify_research.py --skip-browser`는 브라우저를 제외한 범위로 기록합니다. 등록 검증 상태는 엔진·소스·로그가 일치하는 기록이 있을 때에만 새 실행 결과에 첨부합니다. 배포 빌드는 해당 기록이 유효한 경우 함께 포함합니다.

독립 정답 시험은 제품의 지배 관계·선택 함수를 사용하지 않는 Python 전수 계산기와 실제 MCSR 코어 드라이버를 비교합니다. SRD 내부 경로와 전체 망 경로의 탐색 범위를 구분합니다. 고정 그래프의 계산 검증, 시간 모델 비교, 실제 패킷·제어 시스템 비교는 서로 다른 검증 범위입니다. 작은 12위성의 10·30시드 시험은 반복 처리 기능을 검증하며 대규모 성능을 입증하지 않습니다.

INI 상속에서 하위 구성에 경로 기준·서비스 또는 라우팅 유형을 지정하면 상위 구성의 알고리즘 선택보다 우선합니다. 같은 구성에 저장한 알고리즘 선택은 해당 구성에서 우선 적용합니다.

비교 실험은 개별 실행을 보관하고 실험 전체가 완료된 뒤 마지막 실행을 최신 결과로 등록합니다. 취소·실패한 실험에서 이미 계산한 개별 결과는 해당 실행 폴더에서 확인할 수 있습니다. 새 결과는 엔진 요약과 정규화 입력의 모델 식별자가 일치해야 등록됩니다.

복구 기록에는 첫 수신과 안정 복구가 있습니다. 장애 시점에 해당 링크에서 전송·대기 중이거나 최근 실제 ISL 통과가 관측된 흐름을 집계합니다. 최근의 범위는 1초와 설정 송신 간격의 두 배 중 큰 값입니다. 첫 수신은 해당 사건 이후 생성된 패킷의 최초 수신까지 걸린 시간입니다. 안정 복구는 사건 시각부터 나눈 연속 두 개의 1초 구간 각각에서 3개 이상 생성되고, 그중 95% 이상이 관측 종료 전에 수신됐을 때 확인합니다. 안정 복구 시각은 두 번째 구간의 종료와 기준 충족에 포함된 마지막 수신 중 늦은 시각입니다. 같은 링크의 다음 전이 또는 실행 종료에서 관측을 마감합니다. 조건을 충족하지 못하거나 관측이 부족하면 값이 비어 있습니다.

검증 표시는 코어·커널·통합, 대규모 부하, 장시간 제어의 기록을 각각 조회합니다. 대규모 부하는 1,584위성 시험을, 장시간 제어는 132위성에서 600초의 제어 패킷 시험을 표시합니다. 각 기록은 해당 엔진·소스와 검증 산출물 해시가 맞을 때 사용합니다. 장애 검증 기능의 근거는 기본 커널·통합 시험에 있으며 장시간 제어 기록은 그 시험 규모의 지속 부하를 확인합니다.

라벨 제한의 제거·거절 횟수는 `operations.capEvict`, `operations.capReject`와 `approximation`에 저장합니다. 제한이 발생하면 근사 계산으로 표시하며, 미발생 상태가 모든 경로의 전역 최적성을 보증하지는 않습니다. 기존 결과에 이 계측이 없으면 미계측으로 표시합니다. 원본 코어의 미세 지연 동률 처리와 라벨 제한 민감도는 원본 회귀 시험 로그에 보존합니다.

MCSR의 접속 위성 선택은 접속 링크와 이후 경로의 예상 지연 합을 사용합니다. 논문의 SRD 내부 이웃 수 기반 접속 정책과 구분합니다.
TS·HR은 설정된 제약을 충족하는 경로가 없을 때 대체 경로를 사용할 수 있습니다. 전달률과 수신 지연은 패킷 결과이며, 서비스 제약 충족 여부는 별도로 집계하지 않습니다. 도착 기반 라우팅 지터의 초기값은 0이므로, 경로 평가에 사용한 0은 실제 지터가 0으로 관측됐다는 뜻으로 해석할 수 없습니다.

첫 배포 엔진 1.0.0 / 모델 `leo-research-1.0.0`은 비대칭 링크 비용에서 Dijkstra의 목적지 기준 탐색에 역방향 인접 목록을 사용하도록 수정했습니다. 원본 MCSR 헤더는 변경하지 않았습니다. 이전 결과는 계속 재생할 수 있으며, 다른 엔진·모델·측정 구간의 결과는 동일 조건으로 판정하지 않습니다. 이 검증은 자체 모델을 대상으로 하며 논문 재현·실제 위성망·별도 PC의 독립 재현을 인증하지 않습니다.
